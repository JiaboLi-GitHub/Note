# 1 流程架构

1. 创建vulkan单例：设置应用程序信息，指定启动的层和扩展。
2. 启用校验层：创建回调函数处理校验层消息，注册调试信使。
3. 创建窗口表面：基于UI库创建窗口表面。
4. 选择物理设备：选择合适的物理设备，主要从支持的队列族、支持的扩展、是否支持窗口表面、性能等考虑。
5. 创建逻辑设备和队列：创建与物理设备交互的逻辑设备，并获取队列句柄。
6. 创建交换链：
7. 创建渲染通道
8. 创建图形管线
9. 创建指令池
10. 创建指令
11. 创建同步对象

# 2 Vulkan实例

Vulkan实例是应用程序与Vulkan驱动的连接对象。

创建时需要提供应用程序信息，扩展列表、层列表。

# 3 层

层通过拦截调用提供额外服务，主要用于调试、验证和性能分析。

常见的层有校验层和同步层。

# 4 扩展

扩展可以在不改变核心规范的前提下增强功能，支持新硬件特性或平台特性。

通过动态加载的方式获取函数:

```c++
PFN_vkVoidFunction vkGetInstanceProcAddr(VkInstance instance, const char* pName);
PFN_vkVoidFunction vkGetDeviceProcAddr(VkDevice device, const char* pName);
```

层与扩展的对比：

| 特性         | 层                                      | 扩展           |
| ------------ | --------------------------------------- | -------------- |
| 功能定位     | 调试、验证、分析Vulkan                  | 扩展Vulkan功能 |
| 生效方式     | 拦截API调用，在驱动和应用之间插入中间层 | 新增API功能    |
| 生成环境使用 | 通常关闭                                | 通常开启       |

# 5 窗口表面

窗口表面是Vulkan与具体窗口交互的抽象接口。但是Vulkan是一个平台无关的API，它不能直接和窗口系统交互，即无法直接创建窗口表面。所以窗口表面依赖于平台扩展，可以使用GUI库创建窗口表面，如GLFW，QT。窗口表面对物理设备的选择有一定影响，所以需要在选择物理设备之前创建。

窗口表面的图像由呈现队列提供，呈现队列不一定等于图形队列，但大多数情况相同。

# 6 物理设备和队列族

Vulkan支持选择一个或多个物理设备，并且提供了物理设备信息查询的函数，开发者可以根据物理设备信息选择合适的物理设备。

可查询的物理设备信息如下：

1. 基础信息：物理设备名称、设备支持的最高Vulkan版本。
2. 设备特性：是否支持几何着色器、是否支持64位浮点数运算、是否支持光线追踪管线。
3. 设备扩展：支持的扩展。
4. 队列族：支持的队列族。
5. 表面支持：是否支持指定的窗口表面、支持的呈现模式、支持的图像格式。
6. 内存模型

队列族是一组功能相似的队列集合，单个GPU可包含多个队列族，单个队列族可支持多种操作，单个队列族可包含多个队列。

# 7 逻辑设备与队列

逻辑设备作为物理设备的抽象接口，通过显式指定功能集（层、扩展、队列族）实现应用程序与硬件的交互，支持命令提交和资源管理，可兼容不同的物理设备。

创建逻辑设备时，需要指定：

1. 物理设备
2. 队列族
3. 启用的扩展
4. 启用的层（已过时）
5. 启动的特性：是否支持几何着色器、是否支持64位浮点数运算。

创建成功后，可以从逻辑设备中获取队列。队列是逻辑设备的一部分，由逻辑设备创建并管理，用于存储命令，物理设备会从设备队列中读取命令并执行。

# 8 交换链

交换链是一组图像缓冲区，负责管理渲染缓冲区、协调GPU与显示器的工作节奏，确保画面平滑无撕裂。

可设置的关键参数：

**8.1 呈现模式**

呈现模式（presentMode）决定图像何时被提交到屏幕以及如何处理队列中的图像。核心呈现模式有四种，另外有三种扩展模式。

1. VK_PRESENT_MODE_IMMEDIATE_KHR（立即模式）：渲染引擎提交的图像立即参与屏幕的扫描，可能出现画面撕裂。
2. VK_PRESENT_MODE_FIFO_KHR（队列模式）：使用队列储存呈现请求的图像，等待垂直同步取出队头的图片。当队列满时，渲染引擎需要进行等待。
3. VK_PRESENT_MODE_FIFO_RELAXED_KHR（松弛队列模式）：与队列模式的区别是，如果错过上一帧的垂直同步，则立即呈现，可能出现画面撕裂。
4. VK_PRESENT_MODE_MAILBOX_KHR（邮箱模式）：与队列模式的区别是，使用单条目队列，新的呈现请求回替换旧的请求。队列满时渲染引擎不会等待。

另外三种扩展模式与多屏幕共享交换链相关。

1. VK_PRESENT_MODE_SHARED_DEMAND_REFRESH_KHR （最新就绪队列模式）：与队列模式的区别是，垂直同步时丢弃队列过时的图像，使用最新的图像。
2. VK_PRESENT_MODE_SHARED_CONTINUOUS_REFRESH_KHR （共享需求刷新模式）：渲染引擎和屏幕共享一个图像，需要渲染引擎主动请求刷新。
3. VK_PRESENT_MODE_FIFO_LATEST_READY_KHR （共享连续刷新模式）：渲染引擎和屏幕共享一个图像，屏幕定时刷新。

**选择合适数量的交换链图像：**选择队列模式，避免不必要的硬件负载。选择合适的图像数量，避免帧率下降。

**8.2 图像共享模式**

imageSharingMode（图像共享模式）用于指定多队列族访问图像的同步策略。

|                            | 特性                                                         | 优点                                     | 缺点                                               | 适用场景               |
| -------------------------- | ------------------------------------------------------------ | ---------------------------------------- | -------------------------------------------------- | ---------------------- |
| VK_SHARING_MODE_EXCLUSIVE  | 资源在任一时刻仅被一个队列族独占访问。切换队列族时需显式转移所有权。 | 驱动程序可针对独占访问进行优化，性能最高 | 需要手动管理所有权转移，增加代码复杂度             | 游戏、常规渲染         |
| VK_SHARING_MODE_CONCURRENT | 资源可同时被多个指定队列族访问，无需所有权转移。             | 无需手动管理所有权转移，简化代码         | 驱动程序可能需要额外同步机制，性能可能低于独占模式 | GPU 粒子模拟与渲染并行 |

**8.3 图像使用标志**

imageUsage（图像使用标志）定义图像使用的方式，决定图像可以参与哪些操作。

```c++
// 1.传输操作相关
VK_IMAGE_USAGE_TRANSFER_SRC_BIT = 0x00000001,     // 可作为传输源（如复制、Blit 操作的源图像）
VK_IMAGE_USAGE_TRANSFER_DST_BIT = 0x00000002,     // 可作为传输目标（如复制、加载操作的目标图像）

// 2.着色器访问相关
VK_IMAGE_USAGE_SAMPLED_BIT = 0x00000004,          // 可作为着色器采样图像（通过 sampler 访问）
VK_IMAGE_USAGE_STORAGE_BIT = 0x00000008,          // 可作为着色器存储图像（通过 imageLoad/store 访问）

// 3.附件相关
VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT = 0x00000010,          // 可作为颜色附件（用于渲染到纹理）
VK_IMAGE_USAGE_DEPTH_STENCIL_ATTACHMENT_BIT = 0x00000020, // 可作为深度/模板附件
VK_IMAGE_USAGE_INPUT_ATTACHMENT_BIT = 0x00000080,          // 可作为输入附件（用于着色器读取附件内容）
...
```

**8.4 表面格式**

imageFormat（表面格式）指定图像的通道组成，位深度，数据类型，压缩方式和内存布局等。

**8.5 交换范围**

图片分辨率

**8.6 窗口裁剪**

clipped字段用于控制是否启动窗口裁剪

# 10 渲染管道

图形管线是指将3D数据转换为2D图像的一系列有序过程。

图形管线分为三个阶段：应用程序阶段、几何阶段和光栅化阶段

应用程序阶段由主要由CPU负责，CPU将GPU渲染想要的灯光、模型准备好，并设置好渲染状态，为GPU渲染做好准备。

几何阶段分为顶点着色器、图元装配和几何着色器。

**顶点着色器**：**以单个顶点作为输入，对顶点坐标进行空间转换，由局部空间转换位裁剪空间。**

**几何着色器**：**以一组顶点作为输入，通过新增顶点实现几何形状的变换。**

**图元装配**：**按照指定的图元拓扑类型将顶点装配为图元。**

*裁剪剔除：将不在视锥体范围内的图元裁剪掉。将背面剔除掉。

*透视除法：执行透视除法，把齐次坐标转换为标准化设备坐标（NDC）。

*视口变换：将NDC坐标转换为屏幕坐标。

光栅化阶段分为：

**光栅化**：**把图元映射为屏幕上相应的像素，生成供片段着色器使用的片段。**

**片段着色器**：**计算一个像素的最终颜色**

**测试与混合**：**进行深度测试和颜色混合**

创建渲染通道需要指定以上步骤的详细参数。其中，某些参数可以通过动态状态在命令记录阶段动态更新。

- 视口
- 裁剪矩形
- 线宽
- 深度偏移
- 混合操作中使用的常量因子
- 深度测试的边界值
- 模板测试的参数

# 11 指令

**11.1 指令池**

- 功能：分配和管理指令缓冲，重置时会清空所有指令缓冲
- 特性：与特定队列族绑定，从中分配的指令缓冲仅能提交到同队列族的队列
- 关键标志：
  - `VK_COMMAND_POOL_CREATE_TRANSIENT_BIT`：指令缓冲短期存在
  - `VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT`：允许单独重置指令缓冲
  - `VK_COMMAND_POOL_CREATE_PROTECTED_BIT`：用于受保护的内存操作（如加密渲染）

**11.2 指令缓冲**

- 功能：存储待执行的指令
- 级别分类：
  - 主要指令缓冲：可直接提交到队列，可调用次级指令缓冲
  - 次级指令缓冲：不可直接提交，仅能被主要指令缓冲调用

**11.3 指令**

GPU 执行操作的核心载体，用于指定绘制、计算、内存传输等具体任务。

# 12 描述符

**12.1 描述符池**

- 功能：管理描述符集的分配与回收。
- 关键：创建时需指定各类描述符数量上限及最大集数。
- 操作：可重置以回收所有分配的描述符集。

**12.2 描述符集**

- 功能：存储着色器访问资源（纹理、unform）的绑定信息。
- 特性：从描述符池分配，需匹配描述符布局。
- 用途：绑定到管线，供着色器访问资源。

**12.3 描述符布局**

- 功能：定义描述符的类型、数量和绑定点。
- 特性：作为描述符集的 "格式"，被管线布局引用。
- 作用：确保描述符集与管线、着色器的资源访问需求匹配。

# 13 同步

**13.1 栅栏**（Fence）

- 用途：CPU和GPU同步。
- 特性：具有两种状态，分别是信号和未信号。CPU可以查询其状态，也可以等待其状态变为信号，还可以重置其状态为未信号（CPU无法设置栅栏为信号状态）。

**13.2 信号量**（Semaphore）

- 用途：GPU内部操作同步。
- 特性：具有两种状态，分别是信号和未信号。仅GPU可见。

**13.3 事件**（Event）

- 用途：细颗粒度同步。
- 特性：具有两种状态，分别是信号和未信号。CPU和GPU均可触发事件、重置事件和等待事件。

**13.4 屏障**（Barrier）

- 用途：同一命令缓冲内（可跨队列）的资源同步，分为全局内存屏障、缓冲内存屏障和图像内存屏障。
- 特性：指定源阶段和目标阶段，指定源访问掩码和目标访问掩码。

GPU内部同步选择信号量和屏障，任务协调时选择信号量，资源同步使用屏障。

CPU和GPU同步选择栅栏和事件，单纯需要CPU等待使用栅栏，需要CPU和GPU双向的细颗粒度同步选择事件。

# 14 与OpenGL对比

#### **一、性能优势：精细化控制带来的效率提升**

1. **同步机制：从驱动隐式到开发者显式**
   - OpenGL 依赖驱动自动处理同步，可能因过度同步降低 GPU 并行效率，且额外开销不可控。
   - Vulkan 由开发者手动管理同步（屏障、信号量等），可根据实际依赖调整同步粒度，减少无效等待，充分释放 GPU 并行能力。
2. **管线状态管理：从动态修改到预配置**
   - OpenGL 采用状态机模型，支持动态修改管线状态（如着色器、混合模式），但每次修改会触发驱动层管线重建和状态验证，产生显著开销。
   - Vulkan 采用 “固定管线配置（PSO）+ 有限动态状态” 模式，可预创建多条管线适配不同场景（如材质、光照模式），切换时无重建成本。
3. **多线程支持：从串行到并行提交**
   - OpenGL 受限于全局状态机，无法通过多 CPU 线程并行提交指令，难以利用多核性能。
   - Vulkan 支持多队列机制，允许不同 CPU 线程独立录制命令缓冲，再提交到对应队列，充分发挥多核 CPU 优势。同时还可以合并提交命令。
4. **内存管理：从驱动托管到开发者主导**
   - OpenGL 由驱动管理 GPU 显存，隐式分配可能导致碎片化，且频繁映射 / 解映射操作增加开销。
   - Vulkan 允许开发者手动管理显存：
     - 支持持久映射（Persistent Mapping），减少内存映射的重复开销；
     - 可通过内存块共享绑定多个资源，降低内存申请次数，提升 GPU 缓存合并访问效率。

#### **二、扩展性：灵活适配与跨平台兼容**

1. **层与扩展机制**
   - Vulkan 原生支持 “层（Layer）” 和 “扩展（Extension）”：
     - 层：提供调试、性能分析等工具（如 Validation Layer），不侵入核心逻辑；
     - 扩展：按需启用新功能（如光线追踪、网格着色器），适配硬件特性更灵活。
2. **跨平台一致性**
   - OpenGL 依赖驱动对 GLSL 的解释，不同平台（桌面 / 移动）可能存在实现差异，导致兼容性问题。
   - Vulkan 着色器需编译为标准化的 SPIR-V 中间语言，消除平台间的语法解释差异，显著提升跨平台一致性。

### **总结**

Vulkan 通过提供精细化的接口，让开发者可以根据自己的需求搭建高性能的渲染流程。
